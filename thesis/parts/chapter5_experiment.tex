\section{Эксперимент}

В настоящей главе описаны инфраструктурные и проектные решения, обеспечивающие применимость метода, изложенного в~\textbf{Главе~4}. Последовательно рассмотрены: программная инфраструктура и версия компилятора, состав тестового набора бенчмарков и схема его компиляции, методика подсчёта метрики качества кода, параметры дизайна эксперимента, оценка статистической мощности используемых тестов и санитарные проверки полученных данных.

\subsection{Инфраструктура и среда выполнения}

В качестве среды компиляции и оптимизации используется LLVM версии~16. Принципиально важно использование \emph{legacy pass manager}, который выполняет проходы строго в заданном пользователем порядке, в отличие от \emph{new pass manager}, осуществляющего собственное планирование с инвалидацией результатов анализа. Применение нового pass manager сделало бы каузальный вопрос о влиянии порядка проходов некорректным, поскольку фактический порядок выполнения мог бы отличаться от заданного.

Legacy pass manager включается флагом \texttt{-enable-new-pm=0}, который добавляется первым во все вызовы \texttt{opt} с произвольной последовательностью проходов. Стандартный пайплайн \texttt{-Oz}, используемый для вычисления опорного значения \texttt{baseline\_oz}, не работает в legacy pass manager в LLVM~16; для его расчёта используется new pass manager.

Программная часть эксперимента реализована на Python с использованием стандартных средств параллелизации (модуль \texttt{multiprocessing}). Каждый бенчмарк обрабатывается в отдельном процессе; результаты прогонов одного бенчмарка сохраняются в чекпоинт-файл, после чего объединяются с результатами других бенчмарков в единый набор данных формата Parquet.

\subsection{Тестовый набор бенчмарков}

Тестовый набор объединяет программы из двух источников и содержит 517~бенчмарков.

\subsubsection{Набор lac-dcc}

Набор lac-dcc~\cite{lacdcc_benchmarks} объединяет 28~классических наборов бенчмарков из исследовательской литературы по оптимизации кода: cBench, MiBench, Poly\-Bench, Pro\-langs-C, TSVC, media\-bench, McGill, shootout, stanford\-sorts, flops, olden, ptrdist и др. Каждый бенчмарк представляет собой целую программу, скомпилированную из исходного кода на языке C. Всего в наборе используется 231~программа.

\subsubsection{Набор AnghaBench}

Набор AnghaBench~\cite{daSilva2021anghabench} содержит миллионы извлечённых из открытых исходных кодов функций на языке C; каждая функция представлена как самодостаточный синтаксически корректный фрагмент. Из общего объёма набора в работе используется выборка из 286~функций, отобранных из 146~открытых проектов на GitHub. Имя каждой функции имеет вид \texttt{extr\_<file>\_c\_<function>}, что упрощает классификацию по характеру выполняемой операции (см. раздел~4.4).

\subsubsection{Компиляция в промежуточное представление}

Каждый бенчмарк компилируется в файл LLVM~bitcode (\texttt{.bc}) без применения оптимизирующих проходов командой:
\begin{verbatim}
clang -O0 -emit-llvm -c <source>.c -o <bench>.bc
\end{verbatim}
Скомпилированные \texttt{.bc} файлы сохраняются в директории \texttt{benchmarks/\allowbreak compiled/} и используются как единая точка входа для всех последующих прогонов. Скрипты компиляции (\texttt{src/\allowbreak compile\_\allowbreak benchmarks.py} и \texttt{src/\allowbreak compile\_\allowbreak anghabench.py}) обеспечивают идемпотентность: повторный запуск пропускает уже скомпилированные программы.

\subsection{Подсчёт числа IR-инструкций}

Метрика качества кода --- число LLVM IR-инструкций после применения последовательности оптимизирующих проходов. Вычисляется в два шага:
\begin{enumerate}
    \item Текстовое представление \texttt{.ll} формируется из \texttt{.bc} файла утилитой \texttt{llvm-dis}.
    \item Полученный файл \texttt{.ll} парсится: подсчитываются строки внутри тел функций (между \texttt{define ... \{ ... \}}), исключая продолжения многострочных конструкций (\texttt{switch} с множественными исходами).
\end{enumerate}

В подсчёт включаются только LLVM IR-инструкции согласно категории \emph{instructions} в спецификации языка~\cite{llvm_langref}: \texttt{add}, \texttt{load}, \texttt{store}, \texttt{call}, \texttt{br}, \texttt{ret}, \texttt{alloca}, \texttt{icmp}, \texttt{getelementptr}, \texttt{phi} и др. Из подсчёта исключены: определения глобальных переменных и типов, объявления функций (\texttt{declare}), метки базовых блоков, метаданные, блоки \texttt{attributes}, закрывающие скобки.

Корректность подсчёта проверена на всех 517~бенчмарках путём сопоставления с независимой реализацией, основанной на полном перечне опкодов из спецификации языка~\cite{llvm_langref}.

\subsection{Дизайн эксперимента}

\subsubsection{Параметры прогонов}

Для каждого из 517~бенчмарков сгенерировано по 10\,000~случайных прогонов; общее число прогонов составляет $517 \cdot 10\,000 = 5\,170\,000$. Параметры одной случайной последовательности~$\pi$:
\begin{itemize}
    \item длина $L$ выбирается равномерно из множества $\{10, 11, \dots, 40\}$;
    \item проходы выбираются \emph{без повторений} из 89~доступных проходов (см. приложение);
    \item выбранные проходы расставляются в случайном порядке (равномерное распределение по перестановкам).
\end{itemize}

Значение seed генератора случайных чисел зафиксировано для каждого бенчмарка отдельно, что обеспечивает воспроизводимость результатов и независимость порядка генерации от количества параллельных процессов.

\subsubsection{Опорные значения}

Для каждого бенчмарка перед запуском основного эксперимента вычисляются два опорных значения метрики:
\begin{itemize}
    \item $M_{\text{raw}}$ --- число IR-инструкций в исходном \texttt{.bc} файле без применения каких-либо оптимизаций. Используется в знаменателе формулы исхода $Y = (M_{\text{raw}} - M_\pi) / M_{\text{raw}}$ (раздел~4.1.1).
    \item $M_{\text{-Oz}}$ --- число IR-инструкций после применения стандартного пайплайна \texttt{-Oz}. Используется при построении корреляционного графа для определения выигрышности прогона (раздел~4.6).
\end{itemize}

\subsubsection{Выполнение и сохранение результатов}

Каждый прогон состоит из двух шагов: запуск \texttt{opt} с заданной последовательностью проходов и последующий подсчёт числа IR-инструкций в результирующем \texttt{.bc} файле. Прогон, в котором \texttt{opt} завершился с ошибкой или метрика не была успешно вычислена, помечается соответствующим статусом и исключается из дальнейшего анализа.

Результаты сохраняются в формате Apache Parquet с одной строкой на прогон и полями: имя бенчмарка, последовательность проходов (сериализованная в JSON), длина последовательности, число IR-инструкций после прогона, опорные значения $M_{\text{raw}}$ и $M_{\text{-Oz}}$, статус. Формат Parquet выбран как стандарт для табличных данных большого объёма с эффективным сжатием и поддержкой потоковой обработки.

Из общего числа 5\,170\,000~прогонов 5\,169\,736 (99{,}995~\%) завершились успешно; 264~неуспешных прогона, сконцентрированных в 32~бенчмарках (преимущественно lame, bc, miniGMG), исключены из последующего анализа. Полученные распределения метрик содержательно корректны: число IR-инструкций~$M_\pi$ варьируется в диапазоне от 1 до 66\,908 при медиане~140, опорные значения~$M_{\text{raw}}$ и~$M_{\text{-Oz}}$ --- в диапазонах $[3, 54\,014]$ и $[1, 27\,761]$ соответственно. Полный цикл эксперимента выполнен за 19{,}3~часа на 6~параллельных рабочих процессах; среднее время одного прогона составляет около 13~мс.

\subsection{Статистическая мощность}

Оценка минимально обнаруживаемого размера эффекта определяет, эффекты какой величины метод способен выявить при заданном уровне значимости. Для теста Уэлча на двух выборках одинакового размера~$n$ минимально обнаруживаемый размер эффекта~$d$ Коэна на уровне $\alpha = 0{,}05$ и мощности $1 - \beta = 0{,}80$ приближённо равен $d_{\min} \approx 2{,}8 / \sqrt{n}$.

\subsubsection{Вариант~1 (относительный порядок)}

Доля прогонов, в которых оба прохода пары присутствуют одновременно, составляет около 8~\% при параметрах эксперимента $L \in [10, 40]$ из 89~проходов. На каждый из 517~бенчмарков приходится приблизительно $10\,000 \cdot 0{,}08 \approx 800$ таких прогонов, или $\approx 400$~наблюдений на пару в каждой из двух групп воздействия.

При агрегации по 517~бенчмаркам (глобальный уровень) число наблюдений на пару составляет $\approx 207\,000$, что даёт $d_{\min} \approx 0{,}006$. При агрегации по доменному классу (в среднем 65~программ) --- $\approx 26\,000$ наблюдений, $d_{\min} \approx 0{,}017$. Таким образом, на per-class и per-cluster уровнях вариант~1 надёжно ловит даже малые эффекты по шкале Коэна.

\subsubsection{Вариант~2 (соседство)}

Доля прогонов с конкретной биграммой существенно ниже: для пары $(A, B)$ и параметров $L \in [10, 40]$ в среднем встречается около 31~биграммы $[A, B]$ на каждые 10\,000~прогонов одного бенчмарка. Это даёт $\approx 16\,000$ наблюдений с биграммой при агрегации по всем 517~бенчмаркам и пропорционально меньшие выборки на меньших уровнях агрегации.

Уменьшенная мощность варианта~2 принципиальна: метод выявляет только сильные локальные синергии, в которых эффект непосредственного соседства проходов превышает шум. Конкретное число рёбер, проходящих коррекцию, представлено в~\textbf{Главе~6}.
